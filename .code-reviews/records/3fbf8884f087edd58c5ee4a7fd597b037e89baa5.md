## Summary

Feature 08, the trip itinerary, staged on `develop`. It adds day-by-day activities for each trip. Each activity has a category, optional start and end times, a place, an estimated cost, notes, a manual order within its day and a completed flag. Like trips, activities are stored in on-device SQLite per account and work offline. The only network call is the optional place search in the form.

### Medium (2)
- **src/features/itinerary/presentation/components/TripDaySheet.tsx:28**: The day picker builds one chip per trip day, up to 366, with a new `Intl.DateTimeFormat` for each label, on every render of the activity form, including every keystroke, even while the sheet is closed. *(performance)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed (re-review). `ActivityFormScreen.tsx:97` now memoises `days` on `startDate` and `endDate`. `TripDaySheet.tsx:36` builds the chips in a `useMemo` keyed on `days`, `value`, `language`, `t` and a stable `select`. `select` reads the latest `onSelect` through a ref, so the inline callback the parent passes doesn't rebuild the chips. Typing in the title, notes or cost therefore no longer rebuilds 366 chips. `format.ts:68` caches one `Intl.DateTimeFormat` per language and also caches a language `Intl` rejects as `null`, so it isn't retried. That covers the cost when the chips are rebuilt and the overview's labels. The sheet still renders its chips while closed, but only when the days, the selection or the language changes, so this is acceptable.
  - previous ai_reasoning: `ActivityForm` always renders `<TripDaySheet visible={sheet === 'day'} days={days} …>` (`ActivityFormScreen.tsx:340`), and `days = tripDays(trip)` is recomputed on every render (`ActivityFormScreen.tsx:95`). `TripDaySheet` runs `days.map(… formatDayLabel(date, …))` in its own render before `AppBottomSheet` decides whether to mount anything. `formatDayLabel` calls `formatTripDate`, which builds a new `Intl.DateTimeFormat` on each call (`trips/presentation/format.ts:16`). Each `change()` in `useActivityForm` updates state and re-renders the form. For a year-long trip (`TRIP_LIMITS.maxDurationDays` is 366), each character typed into the title, notes or cost therefore costs 366 `addDays` calls, 366 formatter constructions and 366 chip elements. On Hermes on a mid-range Android device, that is likely to make typing lag. Suggested fix: return `null` from `TripDaySheet` (or render the chips only) when `!visible`, memoise `days` with `useMemo` in the form, and reuse one `Intl.DateTimeFormat` per language for the labels. Not measured on a device.
- **src/features/itinerary/presentation/screens/ItineraryOverviewScreen.tsx:75**: The overview renders every trip day, up to 366 `DayCard`s, in a plain `ScrollView`, and `memo(DayCard)` never takes effect, so any change to the itinerary re-renders all the cards. *(performance)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed (re-review). The overview is now a `FlatList` over `groups.days` (`ItineraryOverviewScreen.tsx:42`) with `keyExtractor` on the date. The title, progress, totals, add button and outside-trip section are in `ListHeaderComponent`, so only the visible window of day cards is mounted. `DayCard` is memoised with `sameDayCard` (line 156), which compares the trip id, the conflict flag, the date, the day number, and the day's activities item by item. That comparison holds because `useItinerary` memoises `groupByDay`, and the slice changes entities only through the Immer-based entity adapter (`writePositions` updates only items whose `sortOrder` changed). Activities that didn't change therefore keep their identity, and cards for unchanged days skip re-rendering. `renderDay` is a `useCallback` on `tripId` and `conflicts`. No `getItemLayout` is given, so RN measures each card as it renders. That is acceptable for variable-height cards and is not a finding.
  - previous ai_reasoning: `Screen` is a `ScrollView`, and `groups.days.map(…)` mounts a card for every trip day at once. The comment at line 112 notes that a trip can be a year long. `DayCard` is wrapped in `memo`, but `groupByDay` builds new `day` objects whenever the `activities` array changes, so every card re-renders, and each one calls `formatDayLabel` (a new `Intl.DateTimeFormat`) and `dayTimeSpan`. The overview stays mounted in the stack under the day and details screens. Ticking an activity done, reordering, or saving one there updates the store and re-renders all 366 cards in the background. The React criteria ask for lists that can grow to be virtualised. Suggested fix: render the days with a `FlatList` (fixed or estimated item height), with the header, totals and outside-trip section as `ListHeaderComponent`. Also pass `DayCard` props that stay referentially stable for unchanged days, for example memoise per-day arrays by date, or compare `day.activities` items shallowly in `memo`. Not measured on a device.

The traveller then gets the generic "Something about this request wasn't right. Please try again." error instead of guidance. *(consistency)*

  - dev_reasoning: N/A

It aborts any search still running, makes no request and sets a new `tooShort` state (line 64). That state shows `itinerary.placeSearch.tooShort` with `{{min}}`, which is added to both `en.ts:396` and `es.ts:402`. The hint clears once the query is long enough. The generic "try again" error can no longer appear for a query that is too short. A sheet-specific string is used rather than `map.searchTooShort`, which is consistent enough.
  - previous ai_reasoning: The Search button is disabled only when `!query.trim()`, so a 1-character query can be searched. `onSubmitEditing` has no check at all, so an empty query can be submitted from the keyboard. `SearchPlaces` rejects anything shorter than `SEARCH_QUERY_MIN` (2) with `badRequest`, and the sheet shows `t(getErrorMessageKey('badRequest'))`, which tells the user to "try again", but retrying can't succeed. The explore map already handles this case with `map.searchTooShort` (`ExploreMapScreen.tsx:154`). Suggested fix: disable the button and ignore submit while `query.trim().length < SEARCH_QUERY_MIN`, and show the same too-short hint as the map, or reuse its string.
