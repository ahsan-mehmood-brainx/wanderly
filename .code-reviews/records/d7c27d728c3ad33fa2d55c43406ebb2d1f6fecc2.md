## Summary

Adds budget and expense tracking (feature 09). It includes SQLite `expenses` and `exchange_rates` tables (migration 4), an owner-scoped `LocalExpenseRepository` with zod-validated rows, and Frankfurter exchange rates behind a SQLite cache with a TTL for `latest` and a nearest-earlier fallback. Conversion uses exact BigInt minor-unit math, and manual rates cover currencies the API doesn't publish. There are create, update, delete and conversion-refresh use cases, an RTK slice with a single-writer lock and request-id staleness guards, and screens for the overview, history, details, the add/edit form and the breakdown. The diff also adds deep links for `/budget/:tripId/...`, a Budget entry card on the trip screen, and en/es strings.

Stack: React (Expo SDK 58 / React Native), reviewed with the React criteria adapted to RN. `tsc --noEmit` and `expo lint` ran clean, and the budget and navigation Jest suites pass (20 suites, 361 tests).

Security looks sound. Every SQL statement is parameterized and filtered by `owner_id`. Creating an expense checks that the trip belongs to the owner, and updates re-read the expense under the owner. Route and deep-link ids go through `parseRouteId`. The rate API is HTTPS, needs no key, and its responses are validated with zod.

### Medium (1)
- **src/features/budget/presentation/hooks/useTripBudget.ts:49**: The first background conversion is never re-run when a save or delete lands while it is in flight, so the overview keeps showing stale, unconverted totals. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `useTripBudget.ts:53` now also watches `running` (`selectBudgetRunning`, `requestId !== null`). When a save or delete lands during the background retry, `invalidateRunningLoad` (`budgetSlice.ts:139`) clears `requestId`, so `running` goes from true to false and the effect dispatches a new `retryConversions`. This can't loop: a retry that finishes sets `converted: true` and a failed one sets `status: 'failed'`. `loadTripBudget` was removed, and `useTripBudget.test.tsx` / `budgetSlice.edge.test.ts` now drive the real `loadTripExpenses` + `retryConversions` path. Original finding: On a first visit, `loadTripExpenses` finishes with `converted: false`, and the effect then dispatches `retryConversions`, whose pending state keeps `status: 'ready', converted: false`. If an expense is created, updated or deleted before that retry finishes, `invalidateRunningLoad` (`budgetSlice.ts:148`) rejects the retry's result and writes `status: 'ready', converted: false` again. Those are the same values as before, so the effect's dependencies don't change and nothing dispatches a new conversion. SQLite holds the converted amounts, but the store keeps the old copy: totals leave those expenses out and the "not converted" banner stays up until the user taps Try again or the screen remounts. A slow network makes this easy to hit (open Budget, add a same-currency expense quickly). `budgetSlice.edge.test.ts:163` misses it because it starts from `loadTripBudget` (`converted: true`) and re-dispatches the retry by hand. Possible fix: have the effect also watch the load's `requestId` (or a "conversion pending" flag), so that a cleared request with `converted === false` triggers a new retry.

- **src/features/budget/presentation/state/budgetSlice.ts:107**: `retryConversions` doesn't de-duplicate a conversion that is already running, so several callers start parallel `GetTripBudget` runs. *(efficiency)*

  - dev_reasoning: N/A
  - ai_reasoning: Fixed. The `retryConversions` condition (`budgetSlice.ts:97`) now refuses a dispatch while the trip has any `requestId` in flight, so mounted screens and repeated taps share one run. `useTripBudget` exposes `converting`, and both `BudgetOverviewScreen` and `SpendingBreakdownScreen` pass it to `UnconvertedBanner` as `retrying`. The hook comment now matches what the code does. Original finding: The condition only blocks while `status === 'loading'`, but a background retry keeps `status: 'ready'`. When `BudgetEntryCard` on the trip screen and the pushed `BudgetOverviewScreen` are both mounted, each effect dispatches its own retry, and pushing the overview while the card's retry runs starts another one. `UnconvertedBanner` has a `retrying` prop that no caller passes, so the Try again button gives no feedback and every tap starts another run. Results stay correct (only the newest `requestId` is accepted, and `basis` guards the writes), but each run repeats Frankfurter lookups and SQLite writes. The comment at `useTripBudget.ts:45` ("Only the first caller loads") is not true for retries. Possible fix: skip the retry when one is already in flight (`requestId !== null`), and pass `retrying` to the banner.
- **src/features/budget/data/CachedExchangeRateRepository.ts:61**: A historical rate is cached permanently under the requested date even when the API answered with an earlier day because that date's ECB rate wasn't published yet. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. A cached historical rate is now treated as final only when `rateDate === date` or the date is at least `SETTLED_AFTER_DAYS` (2) before the device's today (`CachedExchangeRateRepository.ts:68`). Any other cached rate falls back to the `latest` TTL and is fetched again, so a rate cached before the ECB published that day gets replaced. Original finding: A date before the device's local today counts as historical and is never refetched. A traveller well east of CET (for example NZ just after midnight) asks for local "yesterday" before the ECB has published it, so Frankfurter returns the previous working day, and that answer is saved under the requested date for good. Later expenses on that date reuse it, and `needsBetterRate` won't replace it because `updatedAt` is already after the expense date. The rate is labelled with its real `rateDate`, so the effect is a rate one working day off, not a wrong label. Possible fix: cache permanently only when `rateDate === date` or the date is safely in the past (or a weekend); otherwise apply the `latest` TTL.
- **src/features/budget/domain/usecases/expenseUseCases.ts:91**: `needsBetterRate` uses `updatedAt` as the time of conversion, but any edit changes `updatedAt`. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `needsBetterRate` (`expenseUseCases.ts:91`) no longer reads `updatedAt`. It checks the stored rate itself: always for `fallback`, and for an API rate when `rateDate < expense.date` and the date has passed. Editing only the title or notes can no longer lock in the pre-date rate. Weekend or holiday expenses still qualify every load, but the rate cache answers them (they're final once settled), and `sameConversion` skips the write when the rate hasn't changed. Original finding: Take a future-dated foreign expense converted at the `latest` rate. Once its date passes it should get that day's rate. If the user edits only its title, notes, category or payment method after the date, `UpdateExpense` keeps the old conversion but sets `updatedAt` to now. The condition `localDateAt(expense.updatedAt) < expense.date` then fails, so the approximate pre-date rate is kept permanently. Possible fix: base the check on when the rate was applied (for example, store the conversion time or compare against the rate's fetch time) rather than on `updatedAt`.
- **src/features/budget/domain/budgetCalculations.ts:90**: `convertMinor` returns `Number(bigint)` without checking that the result is a safe integer, and a manual rate has no upper bound (`expenseValidation.ts:74`). *(validation)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `convertMinor` (`budgetCalculations.ts:91`) now throws a `RangeError` when the result exceeds `Number.MAX_SAFE_INTEGER`, and the `try/catch` in `ExpenseConverter` turns that into an unconverted expense. Manual rates are also capped at `EXPENSE_LIMITS.maxManualRate` (1,000,000), and anything larger fails validation as `tooLarge` (`expenseValidation.ts:76`). Original finding: A mistyped manual rate (for example, extra zeros) gives a base amount above `Number.MAX_SAFE_INTEGER`. It is stored imprecisely, possibly as a REAL, and still passes the row schema (`Number.isInteger(1e26)` is true), so the trip's totals are inflated until the expense is edited. It only happens through user error, but a sanity bound is cheap. Possible fix: cap the manual rate (digits or magnitude) and reject a non-safe result in `convertMinor`, which `applyRate` already treats as "can't convert".
